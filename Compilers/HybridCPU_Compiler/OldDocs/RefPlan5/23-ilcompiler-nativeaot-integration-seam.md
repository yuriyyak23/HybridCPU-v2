# 23 — ILCompiler/NativeAOT target-enablement and integration seam

## Goal

Integrate with NativeAOT at the correct layer: ILCompiler/dependency-graph/runtime metadata infrastructure feeds HybridCPU compilation; LLVMSharp is not used as a CIL native compiler.

## Critical audit correction

Do **not** assume NativeAOT/ILCompiler provides a stable generic external-target plug-in API comparable to an LLVM frontend adapter. The exact target-enablement surface is an implementation property of the pinned `dotnet/runtime` baseline and must be proven from live source before coding this phase.

The default planning assumption is therefore:

- `HybridCPU.Compiler.Core` stays independent;
- a dedicated NativeAOT adapter/fork layer owns ILCompiler types;
- target enablement may require maintained changes in the pinned `dotnet/runtime`/ILCompiler target plumbing, object emission, metadata/code-manager integration and runtime-pack build;
- any upstreamable or public extension seam discovered later can reduce that patch set, but RefPlan5 must not depend on one existing unless the Phase 23 spike demonstrates it.

## Mandatory Phase 23A — source-backed integration spike

Before implementation, pin an exact `dotnet/runtime` commit/SDK and produce a checked-in target-enablement map answering, with source references:

1. Where target architecture/OS/ABI identities are declared and validated.
2. How ILCompiler selects target details, instruction set/features and codegen.
3. Which method-compilation/codegen interfaces can be adapted without leaking into Core.
4. Where relocations, symbols, sections and object-file emission are produced.
5. Where ReadyToRun/NativeAOT nodes request GC info, unwind info, EH data, helper imports and method metadata.
6. How dependency analysis/rooting and generic dictionaries/context data reach codegen.
7. How target runtime helpers, startup/runtime libraries and runtime packs are selected/built.
8. Which changes require a maintained `dotnet/runtime` fork/patch set versus an external adapter assembly.
9. Which APIs are public/stable, internal but intentionally patched, or unsuitable for dependence.
10. How version skew is detected deterministically.

**Gate:** no claim that “ILCompiler can request HybridCPU codegen through an adapter” is accepted until this spike compiles one trivial method end-to-end on the pinned source tree and records the actual patch/hook surface.

## Required architecture

```text
Roslyn/C# -> CIL
          -> NativeAOT ILCompiler dependency graph / metadata
          -> HybridCPU.NativeAOT.Adapter   (may live in pinned dotnet/runtime fork seam)
          -> frontend-neutral method compilation request
          -> HybridCPU.Compiler.Core
          -> code bytes + relocations + GC/EH/metadata references
          -> NativeAOT object/dependency graph pipeline
```

Core receives only frontend-neutral requests built from Phase 06/08/22 contracts. It never references `ILCompiler`, `Internal.TypeSystem`, NativeAOT node types or SDK implementation assemblies.

## Required work after the spike

- Pin `dotnet/runtime`, NativeAOT toolchain and supported host SDK versions in provenance.
- Isolate target-specific changes in the smallest reviewed HybridCPU adapter/fork seam.
- Map method bodies, signatures, target layouts, relocatable symbols, helpers, generic/context requirements and method metadata into Canonical IR/compiler requests without weakening CIL semantics.
- Return code/object fragments, relocations, unwind/GC map references, frame data and diagnostics through a versioned adapter contract.
- Preserve NativeAOT dependency analysis/rooting semantics; do not substitute ad-hoc whole-program discovery.
- Ensure helpers/call stubs generated by NativeAOT are compiled or supplied under the same target ABI; no host-architecture code may enter a HybridCPU image.
- Add explicit feature gates for every unsupported node/codegen/runtime requirement; unsupported means deterministic build failure, not fallback to another backend.

## Separation of problems

Phase 23 is only the **compiler integration seam / target enablement**. It does not itself solve:

- final object/link platform support — Phase 24;
- GC/safepoint stack maps — Phase 25;
- EH/unwind — Phase 25;
- runtime helper implementation — Phase 24/25;
- managed/unmanaged thunks/P/Invoke — Phase 25;
- RID/runtime packs/SDK publish experience — Phase 26.

Passing a trivial method through ILCompiler must not be described as “NativeAOT port complete”.

## Determinism / maintenance

The integration baseline is identified by exact source commit plus patch-set digest. Production codegen bounds remain deterministic HybridCPU work-unit limits; ILCompiler integration may fail operationally but cannot use elapsed time to choose a different method body.

Upstream source updates are accepted only after the Phase 23A map and integration tests are regenerated. Compile success against accidental internal API compatibility is not sufficient.

## Tests / acceptance

- Trivial static method end-to-end through the pinned ILCompiler graph into HybridCPU code bytes.
- Call/return, static data, helper reference, relocation and generic/context cases progressively enabled according to Phase 21/22 capabilities.
- Adapter isolation test: Core package graph contains no `dotnet/runtime`/ILCompiler implementation dependency.
- Target-purity test: no host-target relocation, calling convention, register, object format or code bytes appear in HybridCPU output.
- Version-skew/patch-drift test fails with a clear unsupported baseline diagnostic.
- Negative node/feature matrix verifies unsupported GC/EH/interop/runtime requests fail before malformed object emission.

**Acceptance:** on one pinned `dotnet/runtime` baseline, the exact NativeAOT target-enablement patch/hook surface is documented and reproducible, a qualified method can be compiled through ILCompiler into HybridCPU Core, and no assumption of a nonexistent generic external target plug-in API remains in the roadmap.
