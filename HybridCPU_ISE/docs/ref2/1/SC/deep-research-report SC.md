# Аудит SecureCompute в HybridCPU-v2 на зафиксированном SHA

## Краткий вердикт и база исследования

**Вердикт: положительная SecureCompute runtime-активация запрещена.** На исследованном состоянии репозитория существует не secure-execution mode, а **SecureCompute admission/policy scaffold**: типизированные descriptor-контракты, общий runtime-admission service, набор fail-closed классификаторов, отрицательные release-gates и узкая VMX-проекция без backend-authority. Исполнимого пути `secure instruction → SafetyVerifier-owned secure certificate → secure backend effect → evidence → completion → retire` в production composition root не доказано. Более того, собственный regression-тест репозитория фиксирует, что CPU Stage-B enforcement остаётся открытым и что call graph через decode, SafetyVerifier, certificate и issue не доказан. citeturn45view15turn17view0turn18view1

Безопасно сохранять только следующие режимы:

* **SecureCompute disabled/no-emission**, пока compiler/assembler не создаёт secure carriers и внешний код не может внедрить их через публичные descriptor-конструкторы.
* **Admission-only contract testing**, но без заявления, что успешный admission разрешает execution, completion, retire или attestation.
* **VMX fault-only compatibility projection**: текущий VMX certificate привязан к issuer, generation, VT, owner, domain, slot, bundle и replay epoch, однако его свойства `BackendExecutionAuthorized`, `CompletionPublicationAuthorized` и `RetirePublicationAuthorized` жёстко равны `false`. Это положительно подтверждает zero-authority VMX boundary, но не SecureCompute execution. citeturn45view11turn45view22
* **Phase 22 limited release gate в состоянии hard-denied**: текущий тест прямо требует сохранить закрытыми compiler secure emission, nested execution и final release до независимого доказательства одного именованного runtime-пути. citeturn45view20

Обычный disabled path имеет unit-level доказательство: ordinary operation допускается при отсутствующем, disabled и enabled-but-unmaterialized descriptor; non-ordinary operation в текущем `CloseToHSL` path отказывает при тех же состояниях. Однако **полная observational equivalence всей машины** — architectural state, exceptions, memory ordering, FSP decisions, VT scheduling, replay evidence, telemetry, completion и retire — не доказана. Поэтому disabled mode можно считать безопасным только при сохранении no-emission и hard-denied runtime gate, но не считать формально эквивалентным legacy execution. citeturn45view14turn18view1

### Фактическая семантика общего admission service

Текущий `CloseToHSL` implementation исправляет опасную форму, наблюдавшуюся в более раннем `CloseToRTL` snapshot: secure branch теперь выполняется для **любой** `SecureOperationClass != Ordinary`, а не только при `secureDescriptor.IsEnabled`. Затем policy получает даже null/disabled descriptor и должна отказать; после неё имеется дополнительная null-проверка, domain binding и optional memory admission. Текущие tests отдельно проверяют missing, disabled и enabled-but-unmaterialized descriptors для всех non-ordinary classes и требуют `SecureDomainBoundaryDenied`. citeturn46view0turn45view14

Это полезная локальная fail-closed семантика, но она не превращает сервис в архитектурный authority. Его публичный `Validate` вызываем напрямую, результат содержит общий `DomainRuntimeAuthorityResult`, а не opaque object, который может выдать только конкретный live SafetyVerifier после decode legality и Stage-B materialization. Именно поэтому policy-level positive test не доказывает architectural admission. citeturn46view0turn45view15

VMX refactor демонстрирует подходящий архитектурный образец: private issuer seal, issuer generation, single-attempt issuance, exact carrier digest, bundle/slot/VT/domain/replay binding и явное отсутствие backend/completion/retire authority. Но этот механизм типизирован как `VirtualizationAdmissionCertificate`, не содержит SecureCompute и применяется только к fault-only VMX transport. Его нельзя расширять флагом или переиспользовать как универсальную secure capability: SecureCompute требует собственного authority class и иных proof obligations. citeturn45view10turn45view11turn45view22

### Наблюдаемая composition-root картина

На SHA присутствует live pipeline work в `CloseToHSL/Core/Pipeline/`, включая новый `SafetyVerifier.VirtualizationAdmission.cs`, materialization, FSP и SMT changes. Однако SecureCompute-specific tests по-прежнему тестируют общий service напрямую и сами утверждают, что CPU Stage-B hook отсутствует. Следовательно, наличие pipeline/SafetyVerifier инфраструктуры для VMX нельзя считать transitive SecureCompute integration. citeturn44view0turn45view15

Последний коммит добавил полноценные VMX issuer/replay tests, но SecureCompute tests в том же change set были изменены лишь незначительно и сохраняют Phase 20/21/22 как future/preactivation/hard-denied gates. Это сильное историческое свидетельство, что августовский refactor активировал typed VMX admission, но сознательно не активировал SecureCompute execution. citeturn44view0turn45view20

Главный пересмотр базового плана: фразы «implemented», «conformance complete» и «phase complete» допустимы только для **contract/policy/test surface**. Они не должны использоваться для runtime execution, пока нет production call graph и effect evidence. Сам WhiteBook уже вводит это различие, но отсутствующий canonical plan и document-text tests позволяют release claim зависеть от формулировки документа вместо реально достижимого pipeline path. citeturn1view0turn18view2

### Ранжирование

**Release-stopping P0:** SC-B00–SC-B12. Любой из них отдельно запрещает положительную runtime-активацию.

**Architecture-stopping P0 до FSP/SMT enablement:** SC-B13. Даже после появления executor secure path нельзя включать на heterogeneous 8-wide bundle и virtual SMT, пока certificate не связан с placement/replay identity.

**Boundary P0 для заявлений о confidential/attested mode:** SC-B14.

**Future-only hard deny:** SC-B15.

Существующая положительная работа по VMX не снимает ни одного SecureCompute P0 автоматически. Она лишь предоставляет проверенный шаблон certificate issuance и подтверждает, что compatibility boundary можно сделать incapable-by-construction относительно backend, completion и retire. citeturn45view11turn45view22

Критическая граница между **controlled emission** и **positive runtime execution** должна быть отдельным release gate. Controlled emission доказывает только, что compiler/decoder/SafetyVerifier согласованы по carrier shape и что запрещённые carriers fail closed. Она не разрешает backend effect. Положительное исполнение открывается лишь после появления runtime-owned certificate, grant ledger, effect owner, evidence publisher и completion/retire chain. Это соответствует уже реализованному VMX принципу, где admission certificate специально неспособен разрешить backend, completion или retire. citeturn45view11

Rollback не должен означать «выключить UI flag». Для каждого PR rollback condition должен возвращать систему в **no-emission + hard-denied gate**, инвалидировать все descriptor generations/grant epochs/certificates, запрещать restore snapshots нового формата и сохранять ordinary execution trace-equivalent baseline.

## Открытые архитектурные решения

| Решение | Варианты и trade-off | Рекомендация | Proof obligations до кода |
|---|---|---|---|
| **Canonical descriptor owner** | Per-core registry проще, но создаёт cross-core migration и SMT ownership ambiguity; global registry проще для uniqueness, но вводит contention и ordering | Runtime-level registry с per-domain shard, deterministic allocation и explicit core/VT binding | Uniqueness, deterministic lookup, quiescence, destruction, migration ownership, no public materialization |
| **Descriptor carrier** | Full descriptor в context/request удобен, но forgeable и создаёт split brain; opaque reference требует lookup | Только opaque `(DomainId, Generation, RegistrySeal)` reference | Context и request не могут содержать независимые authoritative copies; stale generation fail closed |
| **Secure admission certificate granularity** | Per instruction точнее, но дороже; per bundle дешевле, но опасен при FSP/partial fault; per domain слишком широк | Per accepted uop/operation attempt, допускающий bundle metadata как immutable binding | Exact opcode/operands/VT/owner/domain/source slot/working slot/lane/bundle/replay epoch/carrier digest |
| **Certificate lifetime** | До execute проще; до retire позволяет complete chain, но расширяет replay window | Admission certificate single-use до execution; execution receipt отдельно single-use до completion/retire | No duplicated/copied/foreign/stale use; invalidation on flush, exception, replay epoch change and descriptor revoke |
| **Grant model** | Bearer token проще; subject-bound capability безопаснее; implicit domain rights дешевле, но создают confused deputy | Subject/resource/rights/epoch-bound capability с ledger ownership | Mint authority, attenuation, consumption, revoke propagation, no raw GUID authority |
| **Epoch scope** | Global epoch прост, но чрезмерно инвалидирует; per-resource сложнее; per-domain балансирует | Monotonic per-domain epoch плюс resource generation | Atomic rotate, comparison semantics, wraparound policy, checkpoint integration |
| **Memory-map semantics** | First-match гибок, но order-dependent; priority regions сложны для proof; disjoint closed-world map проще | Reject every overlap; explicit separate shared-buffer map | Checked intervals, deterministic canonicalization, map generation binding, alias/cache/DMA coverage |
| **Shared-buffer semantics** | Shared physical range с per-access policy; copy-in/copy-out staging; encrypted transport | Для первой активации — bounded copy-in/copy-out через IOMMU owner; no direct shared mapping | Direction, lifetime, zeroization, device identity, completion, partial fault and replay |
| **Первый positive operation** | Private load/store даёт ценность, но сразу требует memory/cache/translation; I/O слишком велик; register-local measurement проще | Register-local, no-memory, no-I/O, no-nested, deterministic measured operation | Exact effect set, no hidden state, stable digest, exception/retire semantics, one VT and FSP-safe placement |
| **FSP policy** | Полностью запретить pilfer для secure uops проще; разрешить same-domain pilfer производительнее | Первая активация: запрет pilfer для secure uop. Позже — same-domain/VT pilfer только с post-placement certificate | Ordinary scheduling unchanged; no starvation/deadlock; deterministic deny; exact source/working slot proof |
| **SMT sharing** | Dedicated secure VT упрощает isolation; shared core сохраняет throughput, но усложняет timing/resource policy | Первый release — один secure VT на core и no cross-VT FSP; расширение отдельной фазой | Resource ownership, exception order, replay stability, no cross-VT grant/evidence reuse |
| **Evidence publication point** | После execute доступно рано, но effect может не retire; после retire архитектурно точно; два уровня сложнее | Internal execution receipt после effect; externally visible evidence только после retire | Receipt/evidence distinction, canonical completion identity, no pre-retire host projection |
| **Attestation key owner** | Process-local software key не доказывает platform trust; external service усложняет deployment; test key пригоден только conformance | До выбора platform root не заявлять hardware-grade attestation; использовать test signer с explicit non-production marker | Key provenance, rotation, audience, nonce, measurement chain and no host/guest confusion |
| **Migration trust model** | Same-host migration проще; cross-host требует remote attestation/key wrapping | Первая версия — same-process checkpoint only либо полный deny; cross-host отдельным проектом | Source/destination identity, anti-rollback counter, key transfer, atomic cutover, old-instance invalidation |
| **VMX projection SecureCompute state** | Показывать coarse status удобно guest OS; любой descriptor/evidence detail создаёт leak/backdoor | По умолчанию отсутствующая projection; при необходимости только enum `Unavailable/Denied`, без IDs, epochs или evidence | Closed-world field inventory, read-only behavior, no reconstruction, no mutation and no timing-dependent detail |
| **Nested child intent** | Implicit inheritance удобно, но небезопасно; explicit derivation сложнее | Оставить hard deny до отдельного attenuating derivation protocol | Strict subset rights, child epoch, parent linkage, revoke cascade, bounded depth and cycle prevention |
| **Unknown schema behavior** | Preserve/ignore повышает forward compatibility, но нарушает fail-closed; reject мешает rolling upgrade | Reject unknown authoritative fields; optional non-authoritative extension area отдельно и не подписывает authority | Schema version negotiation before quiescence, no partial restore, canonical serialization |
| **Positive release criterion** | Количество policy tests легко измеримо, но не доказывает runtime; coverage percentage также недостаточен | Один named-path proof manifest: carrier→certificate→grant→effect→evidence→completion→retire | Reachability, ownership, negative bypass closure, deterministic replay, clean-SHA reproduction and rollback |

До начала реализации SC-PR-D и последующих PR необходимо принять первые шесть решений: descriptor owner/carrier, certificate granularity/lifetime, grant model и epoch scope. Без них код неизбежно закрепит скрытый authority в публичных constructors, request DTO или compatibility layer.

До memory/I/O кода должны быть закрыты memory-map и shared-buffer semantics. До execution кода — первый named operation, FSP и SMT policy. До evidence/attestation кода — publication point, audience и key-owner model. До checkpoint/migration кода — trust model и unknown-schema behavior.

## Итоговая release-позиция и пределы доказательства

На SHA `d3814d1f332f083034d3b245f807a45f97792070` проект имеет **полезную fail-closed контрактную основу**, но не SecureCompute runtime:

1. Текущий generic service корректно направляет все non-ordinary secure classes в secure admission и отказывает missing/disabled/unmaterialized descriptor, что устраняет очевидный guard bypass. citeturn46view0turn45view14
2. Descriptor, memory, I/O, grant, completion и migration surfaces существуют как структуры и policies, однако для большинства из них не доказаны canonical owners и production effect callers. citeturn46view1turn46view3turn46view4turn46view5turn46view6
3. SecureCompute не встроен в единственный допустимый legality authority — SafetyVerifier; это подтверждено не только audit interpretation, но и собственным current test text. citeturn45view15turn45view10
4. VMX получил существенно более сильный typed admission mechanism, но он fault-only и incapable of backend/completion/retire by construction. Это следует сохранять как zero-authority compatibility boundary, а не рассматривать как готовый SecureCompute substrate. citeturn45view11turn45view22
5. Phase 22 правильно остаётся hard-denied, compiler secure emission закрыта, nested execution исключена. Снимать этот gate на текущем SHA нельзя. citeturn45view20
6. Отсутствие canonical activation plan из remote tree и зависимость tests от этого пути делают текущий release evidence невоспроизводимым; это самый ранний blocker, который следует закрыть до любых semantic PR. citeturn10view0turn45view15

**Разрешённая позиция продукта:** `SecureCompute = disabled/admission-only experimental contract; VMX = narrow zero-authority fault projection`.

**Запрещённые заявления:** secure VM, private-memory execution, protected DMA/I/O, runtime attestation, migration-safe secure domain, nested secure execution, production secure backend либо limited secure release.

**Условие перехода к controlled emission:** закрыты SC-B00–SC-B06 и существует SafetyVerifier-owned certificate, но execution gate ещё denied.

**Условие перехода к положительному execution:** закрыты все SC-B00–SC-B14, один именованный effect имеет полную цепочку ownership/provenance, negative-positive-determinism-replay tests воспроизводятся из clean detached SHA, а Phase 22 открывается не флагом и не текстом документа, а проверкой release manifest.
