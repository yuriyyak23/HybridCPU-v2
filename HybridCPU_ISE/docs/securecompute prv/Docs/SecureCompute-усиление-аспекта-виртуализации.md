

Нужно усиливать **secure compute** не как ещё один VMX-режим, не как “защищённый VMCS”, и не как набор флагов `VmxCaps`, а как **строгий подтип домена исполнения HybridCPU**: домен с усиленной памятью, усиленными полномочиями, измеряемым происхождением, ограниченной видимостью свидетельств, контролируемым вводом-выводом и проверяемой публикацией результата. Это хорошо ложится на философию HybridCPU-v2: VMX остаётся совместимой поверхностью, а настоящими владельцами являются нейтральные runtime-объекты, полномочия, память, свидетельства, завершение и перенос. 

# 1. Главная идея: secure compute как “усиленный домен”, а не как VMX-функция

В обычной виртуализации главный вопрос звучит так:

**как изолировать гостя от других гостей и от хозяина на уровне исполнения?**

В secure compute вопрос строже:

**как дать домену исполняться так, чтобы даже более привилегированная внешняя среда не могла произвольно прочитать, подменить, расширить или ложно засвидетельствовать его состояние?**

Для HybridCPU это означает, что secure compute должен быть не надстройкой над VMX, а разновидностью домена:

```text
Обычный домен:
  изоляция + полномочия + память + завершение + свидетельства

Защищённый вычислительный домен:
  изоляция
  + измеренное происхождение
  + конфиденциальная память
  + целостность памяти
  + ограниченная видимость хозяина
  + проверяемые свидетельства
  + безопасный ввод-вывод
  + безопасный перенос
  + запрещённые совместимые обходы
```

То есть **secure compute — это не режим совместимости, а усиленная политика владения**.

VMX может только отобразить часть этой модели наружу, если нужна совместимость. Но он не должен решать, защищён домен или нет.

# 2. Новая архитектурная сущность: Secure Compute Domain

Внутри HybridCPU имеет смысл ввести или формализовать отдельную нейтральную сущность:

```text
SecureComputeDomainDescriptor
```

Она не должна заменять `ExecutionDomainDescriptor` или `MemoryDomainDescriptor`, а должна связывать их более строгим договором.

Такой описатель должен отвечать на вопросы:

кто создал защищённый домен;

какой код был измерен перед запуском;

какая политика памяти применена;

какие страницы являются конфиденциальными;

какие страницы являются разделяемыми;

какие свидетельства можно показать гостю;

какие свидетельства можно показать хозяину;

какие события выхода допустимы;

какие гипервызовы разрешены;

какие данные можно включать в снимок;

какие данные должны быть восстановлены только через повторное измерение или повторную выдачу ключей.

Важно: этот описатель не должен быть VMCS-подобной структурой. Он не “хранит VMX-состояние”. Он является нейтральным владельцем политики защищённого домена.

# 3. Secure compute усиливает Legality A|B

В HybridCPU уже есть двухстадийный допуск. Для secure compute его надо сделать строже.

## Legality A

На первой стадии проверяется форма:

команда распознана;

домен существует;

операция относится к допустимому классу;

совместимая VMX-форма, если она есть, не противоречит ABI;

состояние домена допускает обращение.

Но для secure compute этого мало.

## Legality B

На второй стадии добавляется защищённая семантика:

есть ли полномочие на действие внутри защищённого домена;

не нарушает ли операция конфиденциальность памяти;

не требует ли она раскрытия хозяйских свидетельств;

не пытается ли она прочитать защищённое состояние через совместимую VMX-проекцию;

не создаёт ли она публикацию до retire-границы;

не меняет ли она измеренное состояние без новой фиксации измерения;

не превращает ли admitted-denied в backend success.

Именно Legality B становится главным местом secure compute.

Формула:

**обычная совместимая допустимость не означает защищённую допустимость.**

Команда может быть допустима для обычного домена, но запрещена для защищённого.

# 4. Память: конфиденциальность, целостность, происхождение

Наиболее важное усиление — память.

Для secure compute `MemoryDomainDescriptor` должен быть расширен до политики, которая различает как минимум четыре класса страниц:

```text
PrivateSecureMemory
  закрытая память защищённого домена

SharedMemory
  явно разделяемая память для обмена с хозяином или устройствами

MeasuredInitialMemory
  память, включённая в начальное измерение домена

RuntimeMutableSecureMemory
  изменяемая защищённая память после запуска
```

Для каждой страницы или области должны быть заданы:

владелец;

адресное пространство;

эпоха трансляции;

право чтения;

право записи;

право исполнения;

право совместного доступа;

политика включения в измерение;

политика включения в перенос;

политика обнуления при разрушении домена;

политика раскрытия при ошибке.

Важный запрет:

**хозяин может владеть расписанием и ресурсами, но не должен получать произвольное право читать private secure memory.**

Если хозяин должен взаимодействовать с доменом, он делает это через явно разделяемые страницы или через нейтральный канал ввода-вывода, а не через “особое право гипервизора читать всё”.

# 5. Целостность памяти важнее одной только шифрации

Одной конфиденциальности недостаточно. Если память только скрыта, но может быть незаметно подменена, secure compute неполон.

Нужна архитектурная модель целостности:

страница имеет владельца;

страница имеет эпоху;

изменение корня трансляции меняет эпоху;

повторное подключение старой страницы обнаруживается;

подмена страницы другим доменом запрещается;

снимок не может быть восстановлен как “тот же домен” без проверки происхождения.

В терминах HybridCPU это хорошо ложится на уже нейтральные понятия:

```text
DomainTag
AddressSpaceTag
SecondStageRoot
Epoch
```

Для secure compute к ним стоит добавить:

```text
SecureMemoryEpoch
IntegrityDomainTag
MeasurementEpoch
```

Тогда защита памяти не будет привязана к EPT/NPT/VPID/VMID как к каноническим именам. VMX-слой может только показать совместимый результат, если это допустимо.

# 6. Измерение домена

Secure compute требует измерения: система должна уметь ответить, **что именно было запущено**.

Нужна нейтральная модель:

```text
DomainMeasurementDescriptor
```

Она должна включать:

начальный код;

начальные данные;

начальную политику памяти;

начальную политику ввода-вывода;

набор разрешённых гипервызовов;

набор разрешённых проекций;

версию runtime-договоров;

режим переноса;

режим вложенности;

правила раскрытия свидетельств.

Измерение не должно быть VMX-полем. Его нельзя хранить как “VMCS measurement field”. VMX может иметь совместимый способ прочитать часть аттестации, но источник истины — нейтральный измерительный описатель.

# 7. Свидетельства и аттестация

В обычной виртуализации свидетельства отвечают на вопрос:

**почему произошёл выход, ловушка, отказ или завершение?**

В secure compute появляется ещё один вопрос:

**может ли внешняя сторона проверить, что домен действительно запущен в защищённой форме?**

Для этого нужна аттестация, но в терминах HybridCPU её лучше описывать не как “сертификат VMX”, а как **подписанное свидетельство нейтрального домена**.

Архитектурно это может выглядеть так:

```text
SecureAttestationEvidence
  DomainMeasurement
  RuntimePolicyHash
  MemoryPolicyHash
  CapabilityPolicyHash
  MigrationPolicyHash
  EvidenceVisibilityPolicy
  Nonce / challenge
  Signature / hardware root proof
```

Ключевой принцип:

**аттестация не должна раскрывать host-owned evidence.**

Она должна доказывать свойства защищённого домена, но не выносить наружу хозяйские внутренние трассы, кэши, диагностические данные, адреса, внутренние причины планировщика или скрытые состояния платформы.

# 8. Полномочия: secure compute должен быть grant-first

Для защищённого домена все действия должны быть типизированными полномочиями.

Не должно быть общей привилегии вида:

```text
HostCanInspectSecureDomain = true
```

Вместо этого нужны узкие полномочия:

```text
CanCreateSecureDomain
CanMeasureSecureDomain
CanMapSharedPage
CanInjectInterrupt
CanDeliverSecureExit
CanRequestAttestation
CanMigrateSecureDomain
CanDestroySecureDomain
CanZeroizeSecureMemory
CanBindSecureIoQueue
```

Каждое полномочие должно иметь:

выдавшего;

получателя;

область действия;

срок действия;

связь с доменом;

условия отзыва;

политику свидетельств.

Это усиливает исходную философию HybridCPU: **полномочие первично, совместимый флаг вторичен**.

`VmxCaps` не может говорить: “secure compute разрешён”. Он может только отразить совместимость. Реальное разрешение должно исходить из нейтральной системы полномочий.

# 9. Защищённый VMREAD: особенно опасная зона

Secure compute резко повышает требования к VMREAD.

В обычной модели уже нельзя читать VMCS как state store. В secure compute это становится критическим требованием: неправильный VMREAD может стать каналом утечки.

Для защищённого домена VMREAD должен проходить дополнительный фильтр:

```text
decode
→ frozen compatibility alias
→ RuntimeBoundaryAdmissionService
→ secure-domain admission
→ owner lookup
→ evidence policy
→ secure visibility policy
→ neutral read-only source
→ redaction / denial / projection
→ completion fence
→ retire publication
```

Особенно важно:

`GuestPc`, `GuestSp`, `GuestFlags` можно показывать только если защищённый домен разрешает такую видимость;

`GuestCr0`, `GuestCr4` должны оставаться запрещёнными до появления нейтральной модели привилегированного состояния;

`HostCr3` должен оставаться запрещённым;

хозяйские адреса, внутренние корни трансляции, физические указатели, кэши и диагностические причины не должны попадать в проекцию;

если поле не имеет secure visibility contract — отказ.

То есть для secure compute правило ещё строже:

**даже нейтральный владелец значения недостаточен, если нет политики защищённой видимости.**

# 10. Ввод-вывод: главный практический риск

Память можно защитить, но ввод-вывод может разрушить всю модель.

Если устройство напрямую пишет в защищённую память без строгого посредника, домен больше нельзя считать защищённым. Поэтому нужен отдельный нейтральный владелец:

```text
SecureIoDomainDescriptor
```

Он должен определять:

какие устройства разрешены;

какие очереди ввода-вывода принадлежат домену;

какие буферы являются разделяемыми;

какие буферы являются закрытыми;

кто может выполнять отображение DMA;

какие данные должны копироваться через bounce-buffer;

какие события устройства могут быть доставлены в домен;

какие события должны быть преобразованы в нейтральные ловушки;

какие свидетельства об устройстве можно показать домену.

Главное правило:

**устройство не должно становиться обходным путём вокруг MemoryDomainDescriptor.**

Если ввод-вывод не имеет нейтрального защищённого владельца, он должен оставаться denied или mediated через явно разделяемую память.

# 11. Гипервызовы: admitted-denied по умолчанию

Secure compute должен быть особенно строг к гипервызовам.

VMCALL или любой аналогичный вызов нельзя превращать в успешный backend-вызов только потому, что он совместимо распознан.

Для защищённого домена требуется:

нейтральный владелец гипервызовов;

типизированный номер или класс вызова;

политика аргументов;

классификация памяти аргументов;

запрет передачи указателей на private secure memory, если вызов не имеет явного разрешения;

политика свидетельств;

очищение временных буферов;

отдельная публикация результата.

Правильная модель:

```text
VMCALL распознан
→ runtime admission
→ secure-domain hypercall policy
→ typed capability check
→ neutral hypercall owner
→ memory argument classification
→ evidence classification
→ completion fence
→ retire publication
```

Если хотя бы одного звена нет, результат — не “частичный успех”, а отказ.

# 12. Завершение и retire-публикация как защита от утечек

Secure compute должен использовать завершение не только для архитектурной чистоты, но и как механизм безопасности.

Опасность: результат операции может стать видимым слишком рано — через ловушку, лог, диагностическое свидетельство, совместимый VMX-выход или внутренний буфер.

Поэтому защищённый домен должен требовать:

completion не равен publication;

trap не равен authority;

exit reason не равен runtime decision;

retire publication является единственным архитектурным моментом видимости;

до retire нельзя раскрывать гостю или хозяину значения, не прошедшие evidence policy;

при отказе должна публиковаться только разрешённая форма отказа.

Это превращает retire-границу в важный элемент secure compute.

# 13. Перенос и снимки: secure compute не терпит “сырого VMCS”

Перенос защищённого домена сложнее обычного.

Нельзя сериализовать:

VMCS-проекцию как источник истины;

host-owned evidence;

временные ключи платформы;

внутренние адреса хозяина;

кэши трансляции;

непроверенные совместимые поля;

активные указатели;

диагностические причины завершения.

Нужно сериализовать только:

гостевое видимое состояние;

политику домена;

измеренное состояние;

разрешённые гостевые страницы;

классификацию памяти;

политику гипервызовов;

политику ввода-вывода;

политику восстановления;

миграционные свидетельства.

Для secure compute нужен отдельный договор:

```text
SecureMigrationDescriptor
```

Он должен задавать:

можно ли домен переносить;

требуется ли повторная аттестация после переноса;

как защищается образ;

какие ключи используются для переноса;

какие свидетельства пересоздаются;

какие данные обнуляются;

как предотвращается откат на старый снимок;

как меняется epoch после восстановления.

Ключевая формула:

**переносится защищённый домен, а не VMCS и не хозяйские свидетельства.**

# 14. Вложенные домены и secure compute

Nested-направление для secure compute особенно опасно.

Нельзя разрешить вложенному гостю создать “защищённую VM” через Shadow VMCS или VMCS12 как истинный runtime-субстрат. Это немедленно возвращает архитектуру к VMX-владению.

Правильная форма:

```text
SecureChildIntentDescriptor
```

Родительский домен не создаёт напрямую внутренний защищённый VMCS. Он подаёт намерение:

создать дочерний домен;

задать его память;

задать его измерение;

задать его видимость;

задать его гипервызовы;

задать его переносимость.

Дальше это намерение проходит через нейтральный `RuntimeBoundaryAdmissionService` и проверяется системой полномочий.

Для secure compute вложенность должна иметь строгую иерархию:

хозяин не получает лишнего права на ребёнка;

родитель не получает лишнего права на ребёнка;

ребёнок не получает лишнего права на родителя;

свидетельства каждого уровня классифицированы;

память каждого уровня имеет независимую эпоху;

совместимые VMCS12/VMCS02 остаются только проекциями.

# 15. Минимальная архитектурная схема secure compute для HybridCPU

Слои можно представить так:

```text
Compatibility boundary:
  VMX / VMREAD / VMCALL / VMCS vocabulary
  только совместимые имена и проекции

Runtime admission:
  Legality A|B
  RuntimeBoundaryAdmissionService
  secure-domain admission

Authority:
  typed grants
  secure-domain capabilities
  no VmxCaps authority

State owners:
  ExecutionDomainDescriptor
  MemoryDomainDescriptor
  SecureComputeDomainDescriptor
  SecureIoDomainDescriptor
  SecureMigrationDescriptor

Evidence:
  DomainMeasurementDescriptor
  SecureAttestationEvidence
  EvidenceVisibilityPolicy
  host-owned evidence quarantine

Completion:
  TrapCompletionRouteDescriptor
  completion fence
  retire publication

Projection:
  generated read-only compatibility projection
  denied unless neutral owner + secure visibility contract
```

Это сохраняет главное свойство HybridCPU: **истина находится в нейтральных владельцах, а совместимость только отображает разрешённую часть истины.**

# 16. Что должно быть запрещено сразу

Для secure compute следующие вещи должны считаться архитектурными регрессиями:

VMCS как хранилище защищённого состояния;

активный VMCS-указатель как текущий защищённый домен;

`VmxCaps` как право создавать secure domain;

VMREAD private-state без secure visibility policy;

VMWRITE в защищённое состояние через совместимую поверхность;

гипервызов, который получает указатель на private secure memory без явного договора;

checkpoint, содержащий host-owned evidence;

migration image, содержащий VMCS projection как authority;

Shadow VMCS как mutable nested secure state;

ловушка, публикующая host evidence в guest-visible state;

completion без neutral fence;

retire, объединённый с совместимым VMX-exit;

отладочный путь, читающий private secure memory без отдельного debug-capability и отдельной политики измерения.

# 17. Усиление модели отладки

Secure compute почти всегда конфликтует с отладкой.

Поэтому отладка должна быть не “скрытым правом хозяина”, а отдельным режимом домена.

Нужны разные состояния:

```text
ProductionSecureDomain
DebugSecureDomain
TestSecureDomain
```

Для production-домена:

нет произвольного чтения памяти;

нет произвольного чтения регистров;

нет скрытого VMREAD;

нет host-side dump;

нет сериализации внутренних свидетельств.

Для debug-домена:

должно меняться измерение;

аттестация должна честно показывать debug-состояние;

ключи production-уровня не должны выдаваться;

переносимость должна быть ограничена;

гость или доверяющая сторона должны видеть, что это debug-домен.

Иначе отладка становится универсальной дырой в secure compute.

# 18. Ключи и запечатывание состояния

Secure compute требует модели запечатывания данных.

Нужен нейтральный владелец:

```text
SealingKeyDescriptor
```

Он должен связывать ключ не с VMX-режимом, а с:

измерением домена;

политикой домена;

версией runtime-договоров;

эпохой памяти;

политикой переноса;

режимом debug/production;

идентичностью платформы или группы платформ.

Тогда домен сможет сохранять секреты так, чтобы они раскрывались только при восстановлении совместимого измеренного состояния.

Важно:

**ключи не должны попадать в checkpoint как обычные поля.**

Снимок может содержать зашифрованное состояние, но не сам ключ. После восстановления ключ должен быть заново выведен или выдан через аттестованную процедуру.

# 19. Побочные каналы

Строгая доменная модель не устраняет автоматически побочные каналы.

Для HybridCPU нужно явно разделить:

архитектурную безопасность;

микроархитектурную безопасность;

временные каналы;

кэшевые каналы;

каналы через планировщик;

каналы через ввод-вывод;

каналы через завершение и ловушки;

каналы через миграцию.

Secure compute в HybridCPU должен иметь хотя бы классификацию домена по уровню защиты:

```text
SecureComputeLevel.Basic
  архитектурная изоляция и свидетельства

SecureComputeLevel.ConfidentialMemory
  защита чтения памяти хозяином

SecureComputeLevel.IntegrityProtected
  защита от подмены памяти

SecureComputeLevel.SideChannelReduced
  дополнительные ограничения планирования и совместного использования ресурсов

SecureComputeLevel.AttestedProduction
  измерение, аттестация, sealing, строгий перенос
```

Не надо объявлять полную защищённость, если побочные каналы не закрыты. Правильная академическая позиция: **уровень защиты должен быть явно заявлен и проверяем.**

# 20. Практическая дорожная карта усиления

Наиболее правильный порядок усиления secure compute для HybridCPU такой.

Сначала — **SecureComputeDomainDescriptor** и классификация домена. Без этого secure compute будет набором разрозненных флагов.

Затем — **SecureMemoryDomainDescriptor**: private/shared/measured memory, эпохи, запрет host-readable private memory, политика очистки.

Затем — **DomainMeasurementDescriptor**: что входит в начальное измерение, как измерение связывается с политикой.

Затем — **EvidenceVisibilityPolicy** для secure compute: какие свидетельства видит гость, хозяин и внешняя доверяющая сторона.

Затем — **VMREAD secure projection rules**: denied by default, allow only neutral owner + secure visibility contract.

Затем — **SecureAttestationEvidence**: доказательство измерения и политики без протекания host-owned evidence.

Затем — **SecureMigrationDescriptor**: безопасный перенос, защита от отката, пересоздание host evidence.

Затем — **SecureIoDomainDescriptor**: защищённый ввод-вывод, разделяемые буферы, запрет обхода через DMA.

И только после этого стоит открывать более сложные направления: вложенные защищённые домены, privileged-state projection, производительные гипервызовы.

# 21. Как это меняет текущую VMX-совместимость

Для VMX-совместимого фасада secure compute должен выглядеть как ещё более строгая проекция.

Не так:

```text
VMX supports secure compute
→ разрешить VMREAD/VMWRITE/VMCS fields
```

А так:

```text
Secure domain exists in neutral runtime
→ has measured state
→ has secure memory policy
→ has capability grants
→ has evidence policy
→ has projection contract
→ VMX may expose selected compatible vocabulary
```

То есть VMX не получает новой власти. Он получает только новые способы честно сказать:

поле запрещено;

поле недоступно в защищённом домене;

операция распознана, но не допущена;

операция допущена, но denied из-за secure policy;

значение отредактировано политикой видимости;

аттестация доступна через отдельный нейтральный путь.

# 22. Главный вывод

Secure compute органично усиливает HybridCPU именно потому, что HybridCPU уже построен вокруг правильных осей:

домен;

допуск;

полномочие;

нейтральный владелец;

свидетельство;

завершение;

публикация;

перенос.

Но secure compute нельзя добавлять как “ещё один VMX-флаг” или “защищённый VMCS”. Это должно быть усиление всей доменной дисциплины.

Краткая формула:

**secure compute в HybridCPU — это не доверие к VMX, не доверие к VMCS и не доверие к VmxCaps.  
Это доказуемо ограниченное доверие к нейтральному домену, его измерению, памяти, полномочиям, свидетельствам и публикации.**

Именно поэтому правильный следующий архитектурный шаг — не открывать больше совместимых VMREAD-полей, а ввести строгий нейтральный каркас:

```text
SecureComputeDomainDescriptor
SecureMemoryDomainDescriptor
DomainMeasurementDescriptor
SecureAttestationEvidence
EvidenceVisibilityPolicy
SecureMigrationDescriptor
SecureIoDomainDescriptor
```

После этого VMX-совместимость может быть безопасно наложена сверху как проекция. До этого любые “удобные” VMX-пути должны оставаться denied/fail-closed.
