

В предложенном подходе слой виртуализации действительно становится **главной архитектурной площадкой, через которую secure compute проявляется как исполнимая функция системы**. Но он **не должен становиться единственным владельцем secure compute** и не должен превращаться в новый “VMX-защищённый режим”.

Точнее:

> **виртуализация становится главным составным слоем secure compute, но не источником истины secure compute.**

Источник истины остаётся в нейтральной архитектуре HybridCPU: домены, память, полномочия, свидетельства, завершение, публикация, перенос. VMX/VMCS/VmxCaps остаются совместимой поверхностью, а не основанием защищённых вычислений. 

# 1. Что значит “виртуализация становится поставщиком secure compute”

Secure compute почти всегда требует следующих свойств:

изоляция исполнения;
изоляция памяти;
контроль входов и выходов;
запрет несанкционированного чтения состояния;
измеренное происхождение кода;
аттестация;
управляемые гипервызовы;
защищённая миграция;
разделение гостевого и хозяйского свидетельства.

Все эти свойства естественно ложатся именно на **доменную виртуализационную модель**. Поэтому в HybridCPU слой виртуализации становится местом, где protected/secure domain получает практическую форму.

То есть именно через виртуализацию удобно сказать:

“этот код исполняется не просто как поток, а как защищённый домен”;
“эта память принадлежит защищённому домену”;
“эти свидетельства можно показать гостю, а эти остаются хозяйскими”;

“этот гипервызов разрешён, а этот запрещён”;
“это состояние можно перенести, а это должно быть пересоздано”;
“это значение можно показать через совместимый VMREAD, а это должно остаться denied”.

В этом смысле — да, **виртуализация становится главным носителем secure compute как режима исполнения домена**.

# 2. Но она не должна становиться монопольным владельцем

Опасная формулировка была бы такая:

> “secure compute принадлежит слою виртуализации”.

Это неправильно для HybridCPU.

Правильнее:

> **secure compute собирается слоем виртуализации из нейтральных владельцев HybridCPU.**

То есть слой виртуализации не сам “создаёт безопасность”. Он связывает несколько независимых архитектурных подсистем:

```text
Secure Compute Domain
  ← ExecutionDomainDescriptor
  ← MemoryDomainDescriptor
  ← Capability Grants
  ← Evidence Policy
  ← Completion / Retire Policy
  ← Migration Policy
  ← Secure I/O Policy
  ← Measurement / Attestation Policy
```

Виртуализация здесь — **координатор защищённого домена**, а не абсолютный владелец всех решений.

# 3. Почему это важно

Если сказать, что “виртуализация является владельцем secure compute”, легко скатиться к старой ошибке:

Forbidden VMX-owned examples, not implementation guidance:

```text
VMX owns secure mode
VMCS stores secure state
VmxCaps grants secure capability
VMREAD exposes secure values
```

Для HybridCPU это была бы архитектурная регрессия.

В правильной модели:

```text
нейтральный домен владеет состоянием;
нейтральная память владеет трансляцией;
нейтральные полномочия дают право;
нейтральные свидетельства управляют видимостью;
нейтральное завершение управляет публикацией;
VMX только отображает совместимую часть.
```

То есть secure compute не должен становиться “новым VMX”. Он должен быть **усиленным доменным договором**.

# 4. Более точная формула

Я бы сформулировал так:

**В HybridCPU слой виртуализации является главным архитектурным местом сборки secure compute, потому что именно он управляет доменами, границами исполнения, памятью, выходами, гипервызовами и переносом. Но корневая власть secure compute принадлежит не виртуализационному фасаду, а нейтральным runtime-владельцам HybridCPU.**

Или короче:

```text
Виртуализация = плоскость сборки secure compute.
Runtime/domain model = источник истины secure compute.
VMX = совместимая проекция secure compute, если она вообще разрешена.
```

# 5. Как это выглядит в архитектуре

Слой виртуализации должен отвечать за композицию:

```text
создать защищённый домен
→ измерить начальное состояние
→ выделить защищённую память
→ назначить полномочия
→ задать политику свидетельств
→ задать правила гипервызовов
→ задать правила ввода-вывода
→ задать правила миграции
→ обеспечить завершение и публикацию
→ разрешить только безопасные совместимые проекции
```

Но каждый пункт должен иметь собственного нейтрального владельца.

Например:

память защищает `MemoryDomainDescriptor`, а не VMCS;
право на действие выдаёт capability-система, а не VmxCaps;
видимость регулирует evidence policy, а не ExitReason сам по себе;
публикацию выполняет retire-модель, а не VMExit;
состояние исполнения хранит execution descriptor, а не VMCS field store;
миграция переносит домен, а не совместимый VMCS-образ.

# 6. Что именно слой виртуализации “поставляет”

Он поставляет не криптографию сама по себе и не “магическую безопасность”, а следующие архитектурные условия:

**границу домена** — кто внутри, кто снаружи;
**границу памяти** — что private, что shared, что measured;
**границу полномочий** — кто может читать, писать, вызывать, переносить, уничтожать;
**границу видимости** — какие свидетельства можно показать;
**границу завершения** — когда результат становится архитектурным;
**границу совместимости** — какие VMX-поля можно показать, а какие должны быть denied;
**границу миграции** — что сохраняется, что пересоздаётся, что запрещено сохранять.

Это и есть secure compute в духе HybridCPU.

# 7. Что остаётся ниже виртуализации

Ниже слоя виртуализации должны находиться более фундаментальные механизмы:

корень доверия;
измерение;
защита памяти;
очистка памяти;
ключи;
аттестация;
контроль целостности;
политика публикации;
модель полномочий;
модель восстановления.

Их нельзя прятать внутрь VMX-совместимости. Они должны быть нейтральными, чтобы secure compute мог существовать и без VMX-имен.

# 8. Итог

Да, вы понимаете направление правильно, если под этим имеется в виду:

> **слой виртуализации становится главным способом представить secure compute как защищённый исполнимый домен.**

Но это будет неправильно, если понимать так:

> **слой виртуализации сам становится корневым владельцем безопасности.**

Для HybridCPU правильная позиция такая:

**secure compute — это усиленная доменная виртуализация, собранная из нейтральных владельцев HybridCPU. Виртуализация является главным организующим слоем, но не источником истины. VMX/VMCS/VmxCaps остаются только совместимым словарём и поверхностью отображения.**
