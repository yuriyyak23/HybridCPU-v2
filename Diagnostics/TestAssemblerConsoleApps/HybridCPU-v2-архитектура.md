
# Итоговый вывод

**Критической функциональной регрессии после рефакторинга не обнаружено.** Все 12 запусков завершились успешно, коды завершения равны нулю, отрицательные проверки срабатывают ожидаемо, а вычислительные контрольные суммы в сопоставимых сценариях сохранены. 

Однако обнаружены два существенных изменения:

1. **Модель выполняет те же программы примерно в 1,9–2,2 раза больше модельных тактов.**
2. **Часть общей телеметрии памяти перестала заполняться:** в основных режимах `Total bursts` и `Bytes transferred` стали равны нулю.

Первое является либо ожидаемым следствием новой тактовой модели RF-10, либо настоящей регрессией производительности. По одним логам это различить нельзя. Второе уже можно считать **регрессией наблюдаемости**, если отключение старых счётчиков не было намеренным решением.

Эталонный запуск использовал **10 000 повторов**, а новый — **200 повторов**. Поэтому напрямую сравнивать нельзя:

- общее время работы;
- абсолютное число команд;

# 8. Является ли это ошибкой RF-10

Не обязательно.

До RF-10 память могла продвигаться скрытыми внутренними циклами. Тогда внешний счётчик процессора не видел фактическое время памяти:

```text
один внешний такт
→ внутри несколько продвижений памяти
```

После RF-10 предполагается:

```text
один такт процессора
→ один шаг контроллера памяти
```

В этом случае старый эталон с нулевыми ожиданиями памяти был недостаточно реалистичным, а новые 825 ожиданий отражают исправленную модель времени.

Но это должно быть оформлено как **намеренное изменение архитектурной метрики**, а не просто принято как отсутствие регрессии.

Нужна проверка:

```text
новые дополнительные такты
==
ожидаемая задержка MemoryCycleController
```

Если это равенство подтверждается, результат следует классифицировать так:

```text
не функциональная регрессия,
а несовместимое изменение модели времени
```

Если дополнительные такты превышают расчётную задержку памяти, присутствует настоящая регрессия.

# 9. Регрессия телеметрии памяти

Это наиболее явное несоответствие.

## Эталон

В основных режимах были большие ненулевые значения:

```text
alu:
Total bursts:       1 434 889
Bytes transferred: 11 479 112

vt:
Total bursts:      25 801 875
Bytes transferred: 206 415 000
```

## После Ref1

Во всех шести основных режимах:

```text
Total bursts: 0
Bytes transferred: 0
```

При этом одновременно регистрируются сотни ожиданий памяти.

Это означает одно из двух:

1. счётчики больше не подключены к новому контроллеру памяти;
2. эти поля теперь измеряют другой, более узкий вид передач.

В любом случае старый смысл телеметрии не сохранён. Эталонные ненулевые значения зафиксированы в исходном отчёте GitHub. ([GitHub](https://raw.githubusercontent.com/yuriyyak23/HybridCPU-v2/master/Documentation/AsmAppTestResults.md))

### Оценка

```text
Функциональная регрессия: не доказана.
Регрессия наблюдаемости: подтверждена.
```

### Рекомендация

Либо снова подключить показатели к `MemoryCycleController`, либо явно переименовать их, например:

```text
Legacy burst counter: unavailable
MemoryCycleController accepted requests: ...
MemoryCycleController completed requests: ...
Memory bytes read: ...
Memory bytes committed: ...
Instruction-fetch bytes: ...
```

Нулевое значение не должно выглядеть как отсутствие памяти, когда в том же отчёте есть 825 ожиданий памяти.

```text
lk:     CrossLaneConflict
```

При этом счётчики конфликтов регистров остаются ненулевыми.

Возможные причины:

- поле теперь показывает последнее окончательное решение, а не последний отказ;
- после отказа значение очищается успешным решением;
- изменился порядок обхода кандидатов;
- изменилась семантика телеметрии.

Это не вызвало функциональной ошибки, но значение поля больше нельзя сравнивать с эталоном без описания новой семантики.

## Маски допустимости потоков

Эталон:

```text
vt/max:
requested=0x3E
ready=0xC4

lk/bnmcz:
requested=0x3E
ready=0x5C
```

После Ref1:

```text
vt/max:
requested=0x77
ready=0x19

lk/bnmcz:
requested=0x77
ready=0xC8
```

Во всех случаях:

```text
masked=0x00
```

и выполнение успешно.

Это может быть законным следствием изменения:

- нумерации внутренних кандидатов;
- упаковки маски;
- привязки потоков;
- порядка готовых групп.

Но план должен содержать явную таблицу соответствия старых и новых битов. Иначе невозможно доказать, что поменялось только представление, а не смысл.

# 18. Рекомендуемые действия

## 18.1. Не заменять старый эталон новым

Старый файл следует сохранить как:

```text
Pre-Ref1 / pre-RF10 timing baseline
```

Новый отчёт должен стать отдельным:

```text
Post-Ref1 functional baseline
Post-RF10 timing baseline
```

Иначе намеренное изменение модели памяти будет смешано с обычной регрессией.

## 18.3. Добавить разложение тактов по причинам

Для каждой программы нужны:

```text
total cycles
fetch-wait cycles
decode/admission-wait cycles
memory-admission cycles
memory-completion cycles
execute-wait cycles
writeback-wait cycles
retire cycles
hazard early-return cycles
```

Особенно нужно объяснить 45 дополнительных тактов на каждую четырёхпоточную эталонную порцию.

## 18.4. Исправить телеметрию памяти

Минимальный набор:

```text
accepted memory requests
completed memory requests
read bytes
committed write bytes
instruction-fetch bytes
data-read bytes
data-write bytes
queue-full cycles
bank-conflict cycles
```

## 18.5. Добавить автоматический порог регрессии

После создания нового post-RF10 эталона:

```text
функциональные сценарии: 100% успешны
контрольные суммы: полное совпадение
physical realization: 1.0
width drops: 0
raw cycle IPC: не хуже эталона более чем на 5%
cycles per reference slice: не хуже более чем на 5%
memory telemetry: не должна необъяснимо обнуляться
```
